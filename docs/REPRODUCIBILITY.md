# Reproducibility notes

This document states which parts of the computation reproduce bit for bit and which only within
the tolerance of the mixed-integer solver, how every time in the results is defined, under which machine
load the times were recorded, construction details of the Texas2k data that the paper does not
state, the run times of a full reproduction, and notes on other platforms. All checks below were
made on the reference machine (Section 7). File names are relative to the repository root;
`<system>` is `tx123bt` or `texas2k`.

## 1. Determinism of each step

| Step | Source of randomness | What reproduces | Checked |
|---|---|---|---|
| Processed data (`scripts/data/prepare_*.py`) | NumPy generators with random seeds 42 (samples) and 7 (split) | bit for bit on the reference platform; other BLAS/LAPACK libraries can change the last digits (Section 7) | both rebuilds reproduce the 14 files of `data/SHA256SUMS` byte for byte |
| Scenario subsets of the full model | one permutation with random seed 42 | bit for bit on any platform | nested subsets tested in `tests/test_data.py` |
| Generator outages | seed crc32(scenario identifier) XOR 12345 | bit for bit on any platform | 24 draws recorded with the original code (`tests/test_outages.py`) |
| Deterministic UC and full model | none, but MILPs solved to a 0.1% tolerance with all cores | only within the MILP tolerance (Section 2) | TX-123BT deterministic UC solved again: 59 of 3,312 unit-hours differ |
| PI-SASR selection (features, design set, GP, active set, baseload units) given the stored reference commitment | random seed 7 | bit for bit | TX-123BT S = 1,000: K = 148, GP coefficient of determination 0.5112988860331589; Texas2k: K = 146, 0.9986947916899996 |
| PI-SASR run at S = 1,000 given the stored reference commitment (reduced MILP, verification, exact objective) | random seed 7 and the reduced MILP | bit for bit on the reference machine | TX-123BT rerun: identical `commitment.csv`, objective 38,369,890.506773256, gap 0.6871504335848581%; Texas2k rerun: identical `commitment.csv`, objective 28,793,578.585584596, gap 0.7142552385492971% |
| Merit-order verification of a stored commitment | none | bit for bit | TX-123BT 38,369,743.7514146, Texas2k 28,766,549.226595618 (relative difference 0) |
| LP evaluation of a stored commitment (`scripts/evaluate.py`) | none (LP with a unique optimal value) | to rounding | all 2,000 scenarios of TX-123BT `pisasr_S1000`: largest relative difference 0; first 20 scenarios of all 22 runs: at most 6.4e-16 |
| Merit-order accuracy check (`scripts/validate_merit_order.py`) | none | bit for bit | both `merit_order_validation.csv` files regenerated byte for byte |
| Summaries, paired intervals, lower bound from stored batches, tables, figures and numbers | none | bit for bit | `--check` identical within 1e-9; the 16 files of `paper_assets/` byte-identical; 419 of 419 numbers agree |
| Other experiments (`scripts/run_experiments.py`, `scripts/run_replication.py`) | random seeds 7, 17, 27 (kernels), 1000 + S' (lower-bound batches), 7 to 47 (design-set draws), and MILPs | experiments without a MILP bit for bit; experiments with a MILP as for PI-SASR | embedding spectrum byte-identical; GP kernel row, budget point (S = 200, budget (15, 10)) and criticality-only `pisasr` row identical up to the last digit |

**Last digit of the experiment files.** The original code re-read and re-wrote an experiment file
each time it added a row, and pandas' default float parser can change the last of the 17
significant digits when it reads a value back. The stored files carry these changes, and
`experiments.upsert_row` keeps the same behavior on purpose. A single row computed again can
therefore differ from the stored row in the last digit (for example `top90_overlap`
0.43333333333333335 against 0.4333333333333333).

## 2. The stored reference commitment

PI-SASR learns criticality under a reference commitment u_ref, the schedule of the deterministic
(expected-value) UC. The deterministic UC is a MILP solved to a 0.1% relative tolerance, so solving
it again can return a different schedule of equal quality:

| System | Stored objective | Re-solved objective | Unit-hours that differ | Baseload units (stored, re-solved) |
|---|---:|---:|---:|---:|
| TX-123BT | 37,763,762.26 | 37,761,075.47 (-0.0071%) | 59 of 3,312 | 64, 65 |
| Texas2k | 22,883,650.62 | +0.0001% | 22 of 13,632 | 58, 58 |

u_ref determines the design-set recourse, the GP, the critical scenarios and the baseload units,
so every PI-SASR number depends on it. The repository therefore includes the stored schedule of the
original run, `results/<system>/runs/deterministic/commitment.csv`, and `run_pisasr.py`,
`run_experiments.py`, `run_replication.py` and `validate_merit_order.py` read it by default
(`--reference results`). With `--reference outputs` they read the schedule written by
`scripts/run_full_model.py --deterministic` to `outputs/<system>/runs/deterministic/`; the
results then agree with the paper only as far as the two schedules agree. Given the same u_ref,
PI-SASR is deterministic: the TX-123BT gap of 0.68715% at S = 1,000 appears identically in the
scaling run, in the component analysis, in the embedding experiment (space `svd5`), in the budget
sensitivity at budget (90, 60), in the criticality-only experiment and in the design-set draw with
random seed 7.

The same holds for the full models: every commitment of the paper is included in
`results/<system>/runs/*/commitment.csv`, so the evaluation-set results can be reproduced exactly
without solving any MILP, whereas a full model solved again agrees with the stored one only
within the MILP tolerance.

## 3. Timing definitions

All times are wall-clock times in seconds.

| Quantity | TX-123BT | Texas2k Series25 | Recorded in |
|---|---|---|---|
| Deterministic UC and full model | solver call only: Pyomo writes the model file, Gurobi reads and solves it; model construction is excluded | model construction and solver call | `solve_time_seconds` of `runs/deterministic/` and `runs/full_S<S>/solve_metrics.csv` |
| Full model at S = 2,500 | as above | model construction, writing the LP file and solver call (the solver call alone took 11,594 s) | `solve_time_seconds`, `lean_solver_only_seconds` |
| PI-SASR | online time from data loading to the end of the merit-order verification: features, design-set dispatches, GP fits, k-means, construction and solution of the reduced UC, verification over all S scenarios; the deterministic UC solution behind u_ref (read from a file) and the exact re-evaluation behind the benchmark gap are excluded | same | `solve_time_seconds` of `runs/pisasr_S<S>/solve_metrics.csv`; the exact re-evaluation in `exact_validation_s` |
| Evaluation of one commitment on 2,000 scenarios | about 340 s | about 1,500 s | not kept in `results/` (TX-123BT: 338 s in a rerun; Texas2k: the time column of the original evaluation files); a rerun writes `evaluation_time_seconds` to `evaluation_summary.csv` in the run folder |

* Because the TX-123BT full-model times exclude model construction and the Texas2k times include
  it, the TX-123BT speedups of Table 3 are conservative (note b of Table 3).
* A rerun of `scripts/run_full_model.py` records both parts separately (`build_time_seconds`,
  `solver_time_seconds`, and `write_time_seconds` for the solution from an LP file) together with
  `timing_basis`, and sets `solve_time_seconds` by the definition of the table above, so new times
  are comparable with the stored ones.
* The time columns of the experiment files (`t_*_s`, `time_s`) are defined in
  `docs/RESULTS_GUIDE.md`. `t_online_s` of the component analysis and the budget sensitivity uses
  the PI-SASR definition above. In `design_set_replication_S1000.csv`, `time_s` is the PI-SASR
  online time for the rows `kind` = `pisasr` and model construction plus solution for the rows
  `kind` = `full`.
* Reference for a rerun (measured in reruns on the reference machine): PI-SASR on TX-123BT at
  S = 1,000 took 75.1 s online (73.6 s stored) and 170.7 s for the exact re-evaluation, and the
  evaluation of its commitment on 2,000 scenarios took 338 s. PI-SASR on Texas2k at S = 1,000
  took 633 s online (671 s stored) and 756 s for the exact re-evaluation, about 23 min in total
  (wall-clock).

## 4. Machine load during the recorded runs

The additional experiments were run as parallel sequences of runs, one or two for each system,
and the start and end times in the original run logs show which of them overlapped:

* **Otherwise idle machine**: the component-timing experiment
  (`results/tx123bt/experiments/component_timing_S1000.csv`, Table 4); the Texas2k experiments
  waited until it had finished.
* **Other experiments running at the same time**: the GP kernels of both systems, the TX-123BT
  embedding comparison, the scenario weights at S = 1,000 of both systems, the lower-bound batches
  of both systems, the criticality-only experiments of both systems, the TX-123BT budget
  sensitivity and the Texas2k budget sensitivity at S = 500 and 1,000 (the last only in part).
* **After all other experiments had finished**, one after another: the Texas2k budget sensitivity
  at S = 2,500 and the scenario weights at S = 2,500 of both systems.
* **Not recorded**: the five design-set draws of Section 6.2
  (`results/tx123bt/experiments/design_set_replication_S1000.csv`), which were run earlier, in a
  series of runs without a log of the machine load, and the runs behind Tables 2 and 3.

The paper uses the experiment files for gaps, costs and active-set sizes, and it quotes two groups
of their times: the lower-bound batch times of Section 4.4 (about 15 min on TX-123BT and 2 h on
Texas2k, stated as approximate figures), which were recorded while other experiments ran, and
the times of the five design-set draws of Section 6.2 (106 ± 47 s for PI-SASR against 525 ± 11 s
for the full model), whose machine load was not recorded. As the paper states, the full-model
times of the draws include model construction, whereas the TX-123BT full-model times of Tables 2
and 3 cover the solver call only (434 s at S = 1,000).

## 5. Data construction details not stated in the paper

### Texas2k Series25

The values in this section were computed from the raw Texas A&M files and from the intermediate
set of 7,500 scenarios that `scripts/data/prepare_texas2k.py` writes to
`<out-dir>/intermediate/`; they are not stored in `data/` or `results/`.

* **Wind above installed capacity.** Wind is scaled by 41,837 / 9,587 = 4.36 (Series25 over
  ACTIVSg2000 installed wind capacity). The 2016 summer wind output reaches 12,492 MW, 1.30 times
  the ACTIVSg2000 wind capacity, so the scaled wind reaches 54.5 GW against 41.8 GW installed and
  exceeds the installed wind capacity in 8.8% of the scenario-hours of the set of 7,500
  scenarios. Scaled solar never exceeds its capacity.
* **Net-load floor.** The net load is raised to at least 1,000 MW; this changes 8,193 of the
  180,000 values of the set (4.55%).
* **Hard-coded capacities.** `scripts/data/prepare_texas2k.py` does not read the capacities from
  the case files but uses constants:

  | Constant | Value (MW) | Value in the source files (MW) | Difference (MW) |
  |---|---:|---:|---:|
  | `LOAD_PEAK_25` (Series25 summer-peak load) | 85,758.89 | 85,758.89 (sum of the bus loads of the case) | 0 |
  | `WIND_CAP_25` (Series25 wind) | 41,837 | 41,832.3 (222 wind units of the case) | +4.7 |
  | `SOLAR_CAP_25` (Series25 solar) | 32,266 | 32,312.5 (178 solar units of the case) | -46.5 |
  | `WIND_CAP_16` (ACTIVSg2000 wind) | 9,587 | 9,586.78 (ACTIVSg2000 case, not read by the script) | +0.22 |
  | `SOLAR_CAP_16` (ACTIVSg2000 solar) | 651 | 650.97 (ACTIVSg2000 case, not read by the script) | +0.03 |

  The case totals count all wind and solar units, including the 95 whose status in the case is
  out of service; both the constants and the case give 74.1 GW of wind and solar, as the paper
  states. The 2016 peak load that scales the load (66,275.70 MW) is computed from the time series.
* **Unit status.** The status column of the case is not used: the 568 committable units include
  211 units whose status in the case is out of service.
* **Generator parameters.** Startup costs, no-load costs, ramp limits, minimum up and down times
  and initial status are fuel-class defaults, and 18 units whose minimum output in the case is not
  below their maximum receive 10% of their maximum as minimum output (`data/README.md`).

### TX-123BT

* The scenarios are built around a single baseline day, the day with the largest summer net load
  (2021-08-30), from the June to August deviations of 2017 to 2021.
* The copula draws are independent between hours: the scenarios carry the correlation between
  load, wind and solar within an hour but no correlation between hours.

## 7. Platform notes

* **Reference machine.** Apple M2 Ultra (24 CPU cores, 192 GB of memory), macOS 26.6 (arm64),
  Python 3.11.15 (conda-forge), NumPy 2.4.6, pandas 3.0.3, SciPy 1.17.1, scikit-learn 1.9.0,
  Pyomo 6.10.0, gurobipy 13.0.2 (Gurobi 13.0.2), matplotlib 3.10.9 and openpyxl 3.1.5. The results
  of the paper were computed on this machine; other platforms have not been tested.
* **BLAS/LAPACK.** The TX-123BT scenario generator draws multivariate normal samples through an
  SVD, and the Texas2k generator uses a correlation matrix and a Cholesky factor. Another
  BLAS/LAPACK library (or another NumPy build) can change the last digits of the regenerated
  scenarios, so their checksums will not match `data/SHA256SUMS`. Compare regenerated files with a
  numerical tolerance, and use the files included in `data/` to reproduce the paper: small changes
  in the scenarios change the MILPs.
* **Selection on other platforms.** The embedding (SVD), the GP fit (L-BFGS-B with four restarts)
  and k-means also use floating-point linear algebra. On another platform the GP ranking can change
  where predicted costs nearly tie, which changes the active set. The bit-for-bit agreement of
  Section 1 was checked on the reference platform only.
* **Gurobi.** Gurobi is deterministic for a given version, parameter set, platform and thread
  count. No thread count is set, so Gurobi uses all cores, and a machine with a different number
  of cores can follow another search path and return another incumbent within the 0.1% tolerance.
  `NodefileStart=8` lets Gurobi write node files to the current folder once the branch-and-bound
  tree exceeds 8 GB, so run the scripts from a folder with free disk space. The Gurobi log warns
  that `Crossover=0` is ignored for these MILPs (`docs/MODEL.md`, Section 2).
* **Gurobi license.** Every MILP and LP needs a license that allows models of this size (the
  size-limited license installed with `gurobipy` does not); free academic licenses are available.
  The README gives a command that checks the license, and the tests marked `gurobi` are skipped
  when the license cannot solve a model above the size limit.

## 8. Comparing a rerun with the reference results

A rerun writes to `outputs/` (or to `$PISASR_OUTPUT_DIR`) with the folder names of `results/`. The
three scripts that summarize results read `results/` by default and then rewrite
`results/<system>/summary/` and `paper_assets/` in place (with identical content while `results/`
is unchanged). To compare a rerun, give them `--results-dir outputs`:

```bash
python scripts/summarize_evaluation.py --results-dir outputs
```

```bash
python scripts/paired_cost_difference.py --results-dir outputs
```

```bash
python scripts/make_paper_assets.py --results-dir outputs --out outputs/paper_assets
```

`outputs/paper_assets/numbers.md` then compares every number printed in the paper with the value
computed from the rerun, at the printed precision. Wall-clock times, and the speedups computed
from them, are marked `time differs` when they differ, and are not counted as differences.
Suggested tolerances for comparisons of single values:

| Quantity | Tolerance on the reference platform | On another platform |
|---|---|---|
| Processed data, PI-SASR selection, merit-order values, statistics and assets | exact | numerical tolerance (for example 1e-9 relative) for the data; the selection can differ |
| LP evaluation of a stored commitment | 1e-6 relative (observed: exact to 6.4e-16) | 1e-6 relative |
| Objectives and commitments of MILPs (deterministic UC, full model, reduced UC, batches) | 0.1% relative (the MILP tolerance); PI-SASR given the stored u_ref is exact | 0.1% relative |
| Times | not reproducible; compare orders of magnitude | |
